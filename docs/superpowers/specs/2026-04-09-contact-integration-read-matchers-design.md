# Contact Integration Read Matchers Design

## Goal

Stabilize the contact read integration tests in
`pylon_service/tests/integration/contact/test_reads.py` by replacing assertions on
volatile chain-derived values with explicit matchers.

The work must stay scoped to the integration test file. It must not change the
prepared snapshot image, snapshot directories, or contact implementation code.

## Current Problem

The read integration suite currently compares several full payloads against
literal chain values such as:

- block hashes
- timestamp milliseconds in the `Timestamp.set` extrinsic
- call hashes
- extrinsic hashes
- large opaque hex payloads returned from chain-generated extrinsic arguments

Those values are not stable enough across prepared-chain rebuilds, even when the
overall block structure and semantic content remain correct. As a result, the
tests fail for reasons unrelated to contract regressions in `TurboBtContact`.

## Approach

Keep the existing full-structure assertions, but replace only volatile leaf
values with `dirty_equals` matchers embedded directly in the expected payloads.

The test module should use `dirty_equals` primitives such as `IsStr` and
`IsInt`, then keep plain equality assertions with the matcher-bearing expected
payload on the left-hand side.

This keeps the tests readable and preserves the current intent: compare whole
payloads, not piecemeal fragments, while acknowledging that some chain-returned
values are nondeterministic.

## Stable vs Volatile Fields

Keep exact assertions for:

- snapshot block number
- extrinsic ordering and count
- call module, function, and index
- extrinsic index and length
- subnet, neuron, commitment, and certificate payloads that are intentionally
  fixed by the prepared chain

Relax only fields that are generated by the chain and are not semantically
important to the contact contract:

- block `hash`
- timestamp extrinsic `call_args[0].value`
- `call_hash`
- `extrinsic_hash`
- large opaque hex payloads such as `MevShield.announce_next_key` argument data

## Verification

The change is complete when:

- `pylon_service/tests/integration/contact/test_reads.py` uses `dirty_equals`
  expectations for volatile chain leaves
- `pylon_service/pyproject.toml` adds `dirty-equals` to the existing dev test
  dependencies
- exact structure and stable fields remain asserted
- the targeted test file passes with
  `cd pylon_service && uv run pytest tests/integration/contact/test_reads.py -q`
